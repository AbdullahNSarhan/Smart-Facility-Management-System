# LCI-SFM 1.1.0-rc.1 — software release candidate

This release adds a durable notification center, alarm management and an expandable device/endpoint registry. The team's three preloaded nodes remain the integration baseline for one room and one door. Extra nodes are supported through explicit adapters. Physical hardware is not yet accepted; this is a **software release candidate**, not a claim of a commissioned facility.

## Operator workflows

### Notification Center

The bell shows your unread count and a recent-event preview. The full center filters by search, category, priority, device and UTC-backed date/time range, with pagination. Read/unread state and critical-sound preferences belong to the authenticated account and survive reload/restart. Mark All Read applies only through the latest visible notification ID; events arriving later stay unread.

Authentication successes/logout are private to their account. Rejected sign-ins, administration and diagnostic events are Admin-only. Shared device and alarm notifications are visible to authenticated operators. Anonymous users receive no notification history. Passwords, PINs, verifiers, MQTT secrets and biometric material are not notification content. Existing historical audit events are not backfilled as new notifications on upgrade.

A dedicated authenticated `/ws/notifications` channel sends invalidation only; clients fetch scoped records through the API. A ten-second HTTP refresh fallback also updates counts. Login and error notices from the previous transient toast UI still work; durable events are generated by server activity, not by trusting browser toasts. Cosmetic toast events are not historical audit records.

Repeated rejected sign-ins are grouped within 30 seconds; repeated diagnostic codes per source within 60 seconds; device-config notices within five seconds. Underlying access/management/error audit entries remain separately available. Sound is off by default and applies only to newly observed critical notifications while the page is open, after browser audio permission through user interaction. This is not an OS/background push service.

Admins can set history retention from 7–365 days (default 90). Hourly cleanup deletes old notifications/receipts and old telemetry frames, while preserving the latest frame per boot for replay rejection. Alarm/administration audit is preserved. Retention is not an alarm-clear operation.

### Device Registry

The baseline profiles are seeded once from the existing Node 1/2/3 configuration. Existing room settings and registry edits share built-in names/IPs; optimistic revisions reject stale updates. A maximum of 256 registered devices is supported in this release.

Add Node asks for an immutable lowercase protocol ID, display name, description, location, private IPv4 address, adapter, HTTP port/path and stale interval. Each function has a key, label, kind, unit and optional writable capability. Types:

| Type | Endpoint kinds |
|---|---|
| SENSORS | Numeric sensor values |
| CAMERA | Camera availability and JPEG capture |
| ACCESS | Read-only access state |
| RELAY | ON/OFF switches |
| MIXED | Combination of supported endpoint kinds |

Writable endpoints must be SWITCH with MQTT_V1. Registering an access-controller type does not introduce arbitrary door-unlock commands; the existing team access profile retains its separately allowlisted path. Firmware capabilities and exact physical behavior must be accepted independently.

An enabled device/address/port combination must be unique. The registry accepts RFC1918 literal IPv4 host addresses with final octet 1–254. Endpoints use lowercase letters, digits, underscore and hyphen. HTTP paths cannot contain query parameters, encoded characters or traversal. New devices cannot borrow the legacy profile. Built-in endpoint shapes remain locked for compatibility.

Editing a device does not provision network interfaces, DHCP, firmware or MQTT passwords. MQTT routing uses the immutable ID, not browser-supplied topics. Built-in IP edits remain compatible with the older quick settings dialog. Device status uses actual incoming evidence; registered IP alone never means ONLINE. Values show their own data freshness, separate from heartbeats. Missing values remain missing, not zero.

Disabling retains history, stops ingestion/controls and closes monitoring alarms with an explicit suppression reason. It does not revoke a physical offline controller's access policy. Maintenance has a reason and a bounded expiry (up to 24 hours); it suppresses new monitoring alarms and remote controls, while existing alarms remain visible. End maintenance with duration 0. Expiry resumes evaluation automatically.

Device detail shows reported values, last observation, recent samples, command history, protocol information, diagnostics and relevant controls. HTTP probes are manual, bounded and authenticated. Cameras use a fixed registered destination through a private backend JPEG proxy; redirects and oversized/invalid JPEG bodies are rejected. Camera capture proves neither identity nor liveness.

### Alarm Management

Sensor rules monitor high thresholds with a lower recovery threshold (hysteresis), configurable raise/recovery dwell periods, severity and enabled state. Rules are server-side **monitoring only** and never actuate a relay or door. Units come from the registered sensor; MQ-2 stays raw until calibrated.

One active alarm exists per rule/device condition. Repeated high frames do not flood the inbox. Only fresh numeric evidence advances threshold/recovery dwell; a stale sensor resets pending evaluation and cannot announce recovery. A rule is evaluated using the last reading only while it is within that device's freshness interval.

Alarm lifecycle: ACTIVE → ACKNOWLEDGED → RESOLVED. Acknowledgement records actor/comment/time without implying recovery. Fresh sustained readings below the recovery threshold resolve automatically. Manual sensor resolution requires fresh recovery evidence. Disabling/editing a rule closes its prior alarm with an explicit configuration/suppression reason, then starts new evaluation; it does not claim physical repair.

Missing device or sensor evidence after a configurable grace interval raises a warning. Its wording deliberately allows for a device or transport failure; a healthy broker does not prove a device is healthy. Devices never seen before remain UNKNOWN, with a separate missing-evidence warning after the grace period.

Command failures/timeouts become notifications and alarms with the command ID. Operators can acknowledge or close historical command-failure incidents with a comment. Generic ON/OFF commands are non-retained, expire after five seconds and require an enabled, fresh MQTT device with a writable switch endpoint. Correlated matching ACKs distinguish ACKNOWLEDGED from STATE_REPORTED; timeout, wrong device, late ACK or contradictory state cannot manufacture success. STATE_REPORTED is not independent physical movement verification. Process restart fails pending generic commands without replay.

## Supported adapters and firmware contracts

### MQTT_V1

Register the node before sending frames. Its Mosquitto username must equal its immutable `device_id`. Provision a unique password using the host-side procedure below. Global username-scoped ACL patterns permit only that identity's telemetry/heartbeat/ack publications and command subscriptions. The backend uses its own credential and scoped wildcards. Reserved service usernames cannot be used as additional node IDs.

| Topic | Direction | Payload |
|---|---|---|
| `lci/v1/devices/<id>/telemetry` | Device → backend | Numeric/switch/access values |
| `lci/v1/devices/<id>/heartbeat` | Device → backend | Liveness and optional firmware version |
| `lci/v1/devices/<id>/command` | Backend → device | Expiring switch command; retain=false |
| `lci/v1/devices/<id>/ack` | Device → backend | Correlated device report |

Example sensor/switch frame:

```json
{"schema_version":1,"device_id":"lab_sensor","boot_id":"unique-per-boot","seq":1,"values":{"temperature":25.2,"relay":"OFF"}}
```

Endpoint keys must match the registry. SENSOR values are finite numbers; SWITCH values are `ON`/`OFF`; ACCESS values are `OPEN`/`CLOSED`/`LOCKED`/`UNLOCKED`; CAMERA availability is boolean. This is a v1 adapter contract, not automatic support for every vendor's firmware.

Each boot needs a new ID and monotonically increasing sequence. Duplicate/out-of-order frames do not refresh data age; a previously seen boot cannot replace the current boot. Retained v1 telemetry/heartbeats/ACKs are rejected. Frames larger than 64 KiB are rejected. A heartbeat never refreshes the age of sensor values.

```json
{"schema_version":1,"device_id":"lab_sensor","firmware_version":"bench-1"}
```

Command:

```json
{"schema_version":1,"command_id":"<uuid>","device_id":"lab_sensor","endpoint_key":"relay","value":"ON","issued_at":"<UTC>","expires_at":"<UTC>"}
```

Device reply on its own `/ack`:

```json
{"schema_version":1,"device_id":"lab_sensor","command_id":"<same uuid>","status":"EXECUTED","observed_value":"ON"}
```

ACK status may be ACKNOWLEDGED, EXECUTED or REJECTED. EXECUTED needs the matching observed value to become STATE_REPORTED. Firmware must validate identity, endpoint, expiry and duplicate IDs before actuation. Egress/safety interlocks stay local and independent.

### HTTP_JSON_V1

Test Connection makes one server-side request to the registered private IP, port and path (default `/telemetry`). Return `application/json` with the same v1 frame schema. No redirects, three-second timeout, 32 KiB body limit. Duplicate responses establish reachability without refreshing sensor age. This release does not schedule automatic HTTP polling: arrange repeated manual probes or choose MQTT streaming for continuous monitoring.

### CAMERA_JPEG

Use a private IP, HTTP port and simple path (default `/capture.jpg`). Capture requires an authenticated browser session and fetches through the backend. Four-second upstream timeout, 2 MiB cap, JPEG content type/markers, no redirect following. Frames are returned privately without persistent storage. MQTT mixed-function devices can use the same camera path for capture while telemetry stays on MQTT.

### Legacy team nodes

Existing `lecf/...` contracts remain available. Validated Node 2 numeric data also feeds the new history/rule engine. Legacy heartbeat/status still informs registry liveness. The original three-node health and room pages remain available; the registry handles additional nodes. Secure person/card/PIN policy synchronization and the Vision service remain separate integration work from the prior release.

## Broker provisioning for an additional MQTT device

For an example registered ID `lab_sensor`, on the server checkout:

```bash
docker run --rm -it --user 0:0 \
  -v "$(pwd)/mosquitto:/mosquitto/config" eclipse-mosquitto:2.0 \
  mosquitto_passwd /mosquitto/config/passwd lab_sensor
sudo chown 1883:1883 mosquitto/passwd
sudo chmod 0600 mosquitto/passwd
docker compose restart mqtt-service
```

Do not use `-c` when adding an identity to an existing password file; it would replace the file. Provision the matching secret to the intended device independently; never enter broker passwords into the dashboard, screenshots or Git. Follow [Broker Guide](../mosquitto/README.md) for LAN binding/firewall and existing identities. Broker restart briefly interrupts device connectivity; choose a maintenance window for a connected installation.

## New API map

All paths are under `/api/v1`. Authentication is required. Cookie mutations require CSRF; Admin controls registry/rules/alarm actions/retention. Viewer can read operational data and manage its own notification read state/preferences.

| Method | Path | Purpose |
|---|---|---|
| GET | `/release` | Version, simulator flag, adapter descriptions, monitoring error, retention |
| GET / POST | `/registry` | List all nodes / register a node |
| GET / PUT | `/registry/:id` | Node detail / version-checked update |
| POST | `/registry/:id/maintenance` | Minutes and reason; 0 ends maintenance |
| POST | `/registry/:id/probe` | Bounded manual diagnostic |
| GET | `/registry/:id/snapshot` | Private registered-camera capture |
| GET | `/registry/:id/history` | Latest 100 validated frames |
| GET / POST | `/registry/:id/commands` | History / allowlisted switch request |
| GET / POST | `/rules` | Rules / create sensor rule |
| PUT | `/rules/:id` | Version-checked edit/disable |
| GET | `/alarms` | Filtered paginated alarm list and active count |
| GET | `/alarms/:id` | Evidence and event timeline |
| POST | `/alarms/:id/acknowledge`, `/resolve` | Comment-backed response/recovery |
| GET | `/notifications` | Scoped, filtered inbox and unread count |
| PUT | `/notifications/:id/read` | `{read:true}` or `{read:false}` |
| PUT | `/notifications/read-all` | `{through_id:<last visible ID>}` |
| GET / PUT | `/notification-preferences` | `{critical_sound:<boolean>}` per account |
| PUT | `/retention` | `{days:7..365}`; Admin only |
| POST | `/simulator` | Scenario selector; unavailable outside dedicated simulator |

List filters: `search`, `severity`, `device_id`, `page`, `limit` (max 100), UTC `from`/`to`; notifications also `category`, `unread=true`; alarms also `state`. Device update takes the create payload plus `version`, without server observation fields. Rule update similarly requires `version`.

## Isolated demonstration

From a development checkout with dependencies installed:

```bash
npm ci
npm run simulate
```

Open **http://127.0.0.1:3101**. The initial simulator-only account is `sim_admin` / `LCI-Simulator-Only-2026!`. These defaults apply only to its first isolated database. Its state is stored separately at `data/simulator/lci_sfm.sqlite`; changes persist between simulator starts. The process binds loopback, disables MQTT/upstream probes/physical camera capture and rejects production simulator activation. The ordinary production application has no enabled scenario endpoint.

The banner marks every page as SIMULATION. The three team profiles are present plus `sim_lab` (sensor and relay). Choose Normal, High sensor alarm, Device disconnected or Command timeout. A synthetic camera canvas is labelled as such; no real camera is queried. Simulated control ACKs and state are restricted to this isolated process. This demo does not populate the production database or certify physical behavior.

## Validation and deployment

```bash
npm test
npm run lint
npm run build
npx playwright install chromium
npm run test:ui
```

The browser test starts an in-memory backend and simulated device replies, never a live installation. Optional `UI_SCREENSHOT_DIR` stores sample screenshots. `PLAYWRIGHT_EXECUTABLE_PATH` can select a locally installed Chromium. CI also runs actual Nginx/Node/Mosquitto installation, legacy Node 2 contracts and the new v1 protocol with a cross-identity ACL denial test, command ACK, alarm/notification and recovery, followed by SQLite backup and update-guard checks.

Migration `003_release_operations.sql` is additive. Existing users, secrets, people, credentials, settings and audit rows are preserved. Take a verified backup before deployment; the existing updater remains the deployment path after merge. As with earlier versions, an application rollback does not undo database writes. Review [Release Checklist](RELEASE_CHECKLIST.md) before calling the physical demonstrator accepted.
